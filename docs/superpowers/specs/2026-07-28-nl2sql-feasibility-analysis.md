# 可行性分析：高德 NL2SQL 方案移植到本项目

> **日期**：2026-07-28
> **触发**：阅读高德薛飞跃《NL2SQL 在超大规模数仓场景的架构突破与工程实践》
> （https://mp.weixin.qq.com/s/RDIMNWfITiBqC7e8pBa8bw ）
> **结论状态**：已分析，**暂不改造，仅存档**。后续如推进，优先级见 §6。

---

## 0. 一句话结论

**不要照搬高德的 V2 架构重写（合并成单 Skill）。** 高德 V2 的每一条核心痛点——上下文溢出、9 份重复维护、外部黑盒路由——要么在本项目规模下不存在，要么已经解决。真正值得做的是三件**低成本、高 ROI**的"摘樱桃"改造：表知识卡片化、eval 错误归因、路由表收敛。这三件事会**强化而非削弱**本项目的专利。

---

## 1. 决定性的前提：规模对照（基于仓库实测）

高德整篇文章的逻辑建立在"**超大规模**"上。先看本项目的实测数字（非 CLAUDE.md 概括）：

| 维度 | 高德 | 本项目（实测 2026-07-28） | 含义 |
|------|------|--------------------------|------|
| 业务域 | 9 个 | 6 个 data + 1 fusion（+ viz 层） | 更少 |
| 表数量 | 352 张 | **~18 张**（各 skill `schema.md` + `common_schema` 2 张） | 小一个数量级 |
| references 知识量 | **30,000 行** | **3,305 行** | 是高德的 1/9 |
| 单 skill 最大 references | — | 1,213 行（water-situation） | 单 skill 全量加载无压力 |
| shared 公共层 | V2 才补 | **已存在 1,762 行**（`shared/`） | 已领先 |
| 测试用例 | 900+ | 98 + fusion（`test-cases-with-sql.md` 1,446 行） | — |
| 编排引擎 | 无（V2 单 Skill） | `planner.py` 130 行 + `fusion.py` 424 行 | 已有高德缺的跨域能力 |

**关键推论**：高德做"渐进式加载 + 合并单 Skill"的唯一硬驱动力是 **30,000 行撑爆上下文**。本项目全部 references（3,305）+ shared（1,762）≈ 5,000 行，**现代上下文窗口轻松容纳，无溢出问题**。故高德 V2 的头号卖点对本项目**不成立**。

### 1.1 现状中已有的"V2 级"要素（无需再造）

- **`shared/` = 高德 L4 公共服务层**：`sql_safety_rules / sql_patterns / sql_quality_check / analysis_validation / statistical_methods / data_profiling / db_connection / observability / provenance_footer / sql_dialects / viz_design_principles / common_schema`，1,762 行，按变更频率分层已天然成立。
- **`planner.py` 双图分离**：`BUSINESS_DEPENDENCIES`（确定性执行依赖）与 `CAUSAL_RULES`（带强度评分的数据因果）分离——这是专利核心，高德文章里**没有对应物**（高德只有单层确定性路由）。+ `SKILL_TABLES`（域→表映射）。
- **`water-fusion/SKILL.md` 已含"Skill 关键词映射"表**：确定性路由雏形已存在，只是未收敛为统一 L1。
- **每个 data skill 已有 Validation Gate**：质量基线已建立。

## 3. 三个值得做的改造（若后续推进）

### ① 表知识卡片化（P0，高 ROI，~18 表）

**现状**：`schema.md` 只有"字段/类型/含义"——正是高德点名的"DDL 只有技术元数据"。业务口径（分区裁剪坑、站点编码不一致、阈值缺失、高程基准不一致）散落在 `SKILL.md` Pitfalls 里，**未附着到具体表**。LLM 选表时看不到"此表适用什么场景、口径怎么算"。

**改造**：为核心表补 3 节（高德 S3/S5/S6）：
- **S3 场景映射**：`st_river_r` 适用=河道实时/历史水位；不适用=水库（用 `st_rsvr_r`）、跨年对比（除非带 `tm` 连续区间）
- **S5 口径定义**：把 Pitfalls 硬约束搬到表文档——"z=水位(m)，范围 -1~20m；跨年必须 `tm >= ... AND tm < ...`，禁用 `YEAR(tm) IN`"
- **S6 SQL 模板**：把 `few_shots.md` 高频模板提炼成参数化骨架

**为何收益高**：已知高频错误（占位符污染、分区超时、阈值硬编码）本质都是"口径没在表文档里写死"。卡片化直击这些坑。**且仅 ~18 表，非 352，2-3 天可完成。**

### ② eval 错误归因（P0）

**现状**：`evaluate_skills.py` 已有 `has_valid_response / has_domain_data / has_numeric_data / response_quality / sql_safe` + verifier 层 + `hard_fail`，打分丰富，但**失败用例无"错在哪一环"分类**。

**改造**：加一层归因标签：选表错（关键词映射问题）/ SQL 语法错（模板问题）/ 口径错（S5 缺失）/ 语义模糊（该澄清没澄清）。归因后迭代从"准确率 80%"变成"30% 错在选表 → 优先修路由"，与高德 5.1 一致。

### ③ 路由表收敛成统一 L1（P1）

**现状**：路由能力已分散存在，未收敛——`water-fusion/SKILL.md` 关键词映射 + `planner.py` `BUSINESS_DEPENDENCIES`/`SKILL_TABLES`。但**无对每个查询都跑的统一 L1**：单域靠 hermes 黑盒，跨域才进 fusion。

**改造**：合并成一张确定性 L1 路由表（关键词→候选域 + 歧义消解），让**每个查询**先过它。歧义时给 2-3 候选（如"水位"→ 河道/水库/预警）。

**边界注意**：水利域边界比高德"交易/业财"模糊（水位+降雨+预警常要同时用）。**纯确定性路由须保留 water-fusion 跨域兜底**，勿用规则穷举多域场景。这正是高德 3.2"未来混合架构"方向，而本项目已有 fusion 引擎——比高德更接近该未来态。

## 4. 与专利的关系（战略）

**高德文章恰是本项目专利方向的佐证。** 高德 §7.2 明确把两件事列为**未解决的未来工作**：
1. "取数 Skill 与分析 Skill 的**跨 Skill 知识共享**"
2. "知识本是**图状关联**，树形结构是妥协" → 想做图状知识平台

而本项目 `water-fusion` + `planner.py`（双图分离）+ `fusion.py`（三维关联/融合/冲突消解）**正是 (1) 的工作原型**，且双图设计（`BUSINESS_DEPENDENCIES` vs `CAUSAL_RULES`）在高德文章里**完全没有**。

**含义**：
- 高德在"路由确定性 + 表知识深度"上领先；
- 本项目在"跨域融合 + 知识关联建模"上领先，且这正是高德自承的短板。
- 正确叙事不是"向高德学习重写"，而是"**高德验证了融合创新价值；本项目在路由确定性和表知识深度上低成本补齐，即可形成比高德更完整的方案**"。

**风险警示**：若照搬高德把 6 skill 合并成 1，会**直接掏空专利"多 skill 编排"核心主张**——最该避免的改造。

## 5. 不建议做的事（避免过度工程）

- ❌ 合并单 Skill / 4 层架构重写——规模不支持，且伤专利
- ❌ 建"图状知识平台 / KBase"——为 18 表、5,000 行知识建平台是过早优化（高德自己都还没做出来）
- ❌ DDL 一致性监控、元数据 Pipeline——schema 稳定，手工维护成本低
- ❌ 把确定性路由当银弹——水利域边界模糊，强行穷举会漏多域查询

| 优先级 | 改造 | 预估工作量 | 预期收益 |
|--------|------|-----------|---------|
| **P0** | 表知识卡片化（S3/S5/S6，~18 表） | 2-3 天 | 直接消灭已知高频坑 |
