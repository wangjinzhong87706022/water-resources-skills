## 三、数据证实的真实瓶颈

### 🔴 1. 墙钟几乎全是 LLM 生成，不是 SQL、也不是 matplotlib 渲染

最长几个间隔（85s / 71s / 69s / 53s）全部对齐在**高输出 codegen 调用**上（out 1700–2500 token）。模型是本地 `qwen36-27b-local`（`Qwen3.6-27B-Q5_K_S.gguf`，经 `172.28.101.81:8080`），生成 ~2000 token 就要 60–85s——这是单卡 27B-Q5 的吞吐地板。

> **纠正前一版的错误**：前一版把"生成绘图代码的 LLM 时间"误记为"matplotlib 渲染 59s"，并据此给出"matplotlib 优化省 45s"。实测渲染仅几秒，**matplotlib 不是瓶颈**，瓶颈是 LLM 在写那段绘图代码。

### 🔴 2. `cache_read = 0` 全中（单点最大杠杆，已坐实）

12 次调用的输入从 6,465 单调涨到 28,779，但**没有一次命中 prompt 缓存**，Σ prefill = **238,665 token 全量重算**。

而代码层面**本就是为 prefix-cache 设计的**：
- `deerflow/agents/middlewares/dynamic_context_middleware.py` 注释："kept fully static for maximum prefix-cache reuse across users"
- `system_message_coalescing_middleware.py`："preserving prefix-cache hits"

但模型走本地 llama.cpp，服务端要么没开 prefix caching、要么没在 usage 里回报。注意：代码里的 `skills_system_prompt_cache` 只是**进程内字符串缓存**，不是 token 级 prompt cache，不能算数。

保守估计：稳定的系统提示+skill+历史前缀占每次输入的一半以上。若服务端开 prefix caching（如 vLLM `--enable-prefix-caching` 或 llama.cpp 的对应开关并正确回报 usage），可砍掉一大块重复 prefill 的计算与延迟。

### 🟡 3. 重复整轮查询 + 连画 3 遍图（不是 N+1）

- #3 重复"找测站"
- #6 重复"查月度/年度"
- #7 / #8 / #9 连续画 3 遍图

每次重复都触发**一整轮新的 LLM 调用**（且上下文更大）。这是 agent 循环的决策问题，**不是 SQL 写成 N+1**。

> **纠正前一版的错误**：前一版把"N+1 查询"列为 #1 瓶颈（省 30s）。实测本次对比查询用的是**单条带 `GROUP BY stcd, YEAR(tm), MONTH(tm)` 的批量 SQL**，不存在 N+1。N+1 模式出现在**别的 thread**，被错误挪用到了这次。

### 🟡 4. 两次近空响应浪费 ~28s

#10（out=51）、#11（out=41）几乎没产出，却各耗 13–15s。`loop_detection_middleware` 没拦住这种空转。

### 🟡 5. 分区裁剪 SQL bug（本次实锤）

#5 的 SQL 实际是：
```sql
SELECT stcd, YEAR(tm) yr, MONTH(tm) mo, AVG(z) avg_z, ...
FROM st_river_r
WHERE stcd IN ('HT0021002001000010', ...)
  AND YEAR(tm) IN (2023, 2024)   -- ❌ 无 tm 连续范围
  AND z IS NOT NULL
GROUP BY stcd, YEAR(tm), MONTH(tm)
```
`st_river_r` 是 `RANGE(tm)` 分区表（见 `CLAUDE.md`）。`YEAR(tm) IN (...)` 不给优化器连续区间，**可能扫所有分区**。正确写法：
```sql
WHERE stcd IN (...)
  AND tm >= '2023-01-01' AND tm < '2025-01-01'  -- ✅ 分区裁剪
```

## 六、复测：KV cache 已生效，但负载是 decode-bound（不省延迟）

开启 LLM 服务端 KV cache 后重跑同一问题（run `e3d4e915` / thread `ef13c8e8`，19:11:55）：

| | 旧 run（无缓存）| 复测 run（KV cache on）|
|---|---|---|
| 墙钟 | 434.4s | **434.3s**（无变化）|
| LLM 调用 | 12 | 16 |
| Σ输入 | 238,665 | 321,325 |
| Σ输出 | 12,996 | 14,816 |
| **缓存命中** | 0%（12/12 cache_read=0）| **83.4%**（Σcache 268,034）|

**KV cache 确实生效**（#3–#13 命中 82%~98%；#1/#2 冷启动、#14 另一条前缀子任务未命中）。但墙钟没降，因为：

> **本负载 decode-bound，不是 prefill-bound。** KV cache 只省输入侧 prefill，省不了输出侧 autoregressive decode。

逐调用证据（Δ=墙钟，与 output token 强相关）：

| 调用 | out | Δs | | 调用 | out | Δs |
|---|---|---|---|---|---|---|
| #6 | 1748 | 53 | | #10 | **52** | **3** |
| #7 | 1678 | 43 | | #12 | **48** | **3** |
| #11 | 1800 | 54 | | #15 | **40** | **9** |
| #13 | 1720 | 46 | | | | |

#10/#12/#15 与 #6/#11 是**同样结构**（prefill 都命中缓存），但 output 大则 40~54s、output 小则 3~9s——耗时几乎完全由 output 决定，与缓存无关。

本地 27B（`Qwen3.6-27B-Q5`）decode 速率稳定 **~33 tok/s**（单卡 autoregressive 地板）。复测 Σoutput 14,816 → 14,816/33 ≈ **449s**，正好吃满 434s 预算。autoregressive decode 逐 token 生成，**无法被缓存**。

雪上加霜：复测调用更多（16 vs 12）、输出更多（15k vs 13k），decode 多花的 ~55s 抵消了 prefill 的节省，故表面"无提升"。

**结论**：缓存值得保留（省 token 成本），但**对延迟无效**。降时延的唯一抓手是砍 output token + 砍调用数（见第四节 P0），其次是提升 decode 吞吐（P1）。

## 八、再复测：161.5s 更快，但报告落盘 + 相对路径致图不渲染

第七节修复"嵌图"后再跑（run `99ecf6a2` / thread `8ca2676e`，20:00:55）：**161.5s / 11 调用 / 5342 output**——更快了，但出现新缺陷：**图显示成文字、前端单薄**。

### 缺陷：agent 把完整报告写成了单独的 .md 文件

- 生成了 `outputs/古运河水位对比分析.md`（报告全文）+ `outputs/古运河水位对比.png`（图）。
- 文件里图用的是**相对路径**：
  ```markdown
  ![古运河水位对比](古运河水位对比.png)   ← 相对路径
  ```
  DeerFlow 只在**对话消息**里把**绝对路径** `/mnt/user-data/outputs/...` 重写成 artifact URL 渲染；文件里的相对路径解析不了 → 只剩 alt 文字"古运河水位对比"。
- 对话回复（`last_ai_message`）只是摘要，**无任何 `![]()`**，结尾"完整报告请查阅输出的 Markdown 文件…"→ 前端对话区单薄、无图。
- 实证：gateway 里这一轮**从没 fetch 过**本图的 artifact（只有上一轮 `2023vs2024.png` 的陈旧 GET）。

### 根因与修复

根因：第七节的"把图嵌进报告"被理解成"嵌进我写的那个**文件**"。修复（`water-visualization` 第 7 步 + `water-situation` 交叉引用，已同步 repo 与 hermes）：

1. **对话回复正文就是交付物**：标题/结论/图/表/发现全部写在回复里；**严禁** `open().write()` 另存 `.md` 报告文件（实测：落盘 → 前端只剩摘要 + 图变文字）。
2. **图必须内嵌在回复正文**，且**只能用绝对路径** `/mnt/user-data/outputs/<文件名>.png`；相对路径、或只写进文件里的路径都渲染不出。
3. **落盘文件只留两类**：数据 CSV（查画解耦）+ 图表 PNG。报告文字不落盘。

### 前端层说明

前端对话区是 markdown 渲染器。历史成功显示图的 run 用的就是 `![alt](/mnt/user-data/outputs/...)` **内联绝对路径**，故大概率**无需改前端代码**——只要 agent 交付对的内容即可。兜底：若本次修复后图仍不渲染，则切到 `deer-flow/frontend` 查图片渲染组件（markdown→artifact URL 重写层），那是另一条线。

### 下次重跑验收三点

1. 对话区是否**像 md 一样**显示完整报告（标题/表/结论都在）；
2. 图是否**内联渲染**（非文字、非仅可点链接）；
3. `llm_call_count` 稳在 5~8、墙钟 ≤200s。
