# 水利 Skill 评测报告:9B vs 27B 对比与适用建议

> **报告日期**:2026-08-05
> **范围**:扬州水利 6 个 data skill(water-situation / rainfall / water-quality / water-forecast / gate-pump-operation / water-warning),98 道评测题(L1/L2/L3)
> **评测链路**:DeerFlow Gateway `/api/runs/wait` 真实全栈(自然语言 → agent → SQL → MySQL → 评分),非离线脚本模拟
> **数据来源**:见文末「数据来源」。**所有数字均来自仓库内报告与日志;模型版本部分为推断,已明确标注。**

---

## 0. 摘要(Executive Summary)

| 维度 | 27B(qwen3.6-27B,基线) | 9B(qwen3.5-9B,本周) | 差距 |
|------|------------------------|----------------------|------|
| 全量均分(98 题) | **0.864**(8/3 优化后峰值) | **0.749**(8/4–8/5) | **−0.115** |
| 通过率(≥0.6) | **96.9%** | **89.8%** | **−7.1 pp** |
| 最稳 skill | water-situation / gate-pump | water-situation / gate-pump(同) | 几乎无损 |
| 最弱 skill | water-forecast(0.768) | water-quality(0.575) | 弱项转移 + 放大 |
| 同题稳定性 | 高(Q047≈0.75 稳定) | **低**(Q047 四次跑 0.25/0.30/0.44/0.65) | 9B 高方差 |
| 推理吞吐 | ~33 tok/s(27B-Q5 单卡地板) | 更快(单题均时反而高,见 §3) | — |

**核心结论**:

1. **9B 总体可用但退一档**:通过率从 96.9% 掉到 89.8%,均分 −0.115。退化**不均匀**——简单查表类(water-situation/gate-pump)几乎无损,领域推理类(water-quality 评价、water-forecast)退化最重。
2. **9B 的致命问题不是"答错",而是"不稳定 + 易卡死"**:同题重跑方差极大,部分题陷入 schema 探索死循环产 0 条 SQL;间歇超时(stall)也更频繁。
3. **此前在 27B 上做的 skill 优化(占位符根治、单轮模板、golden SQL 对齐、超时兜底)对 9B 同样有效**,是 9B 还能守住 89.8% 的主因。
4. **本轮针对 9B 的两轮干预**:① serving 修复(坏模型吐 8192 个 `?` 的严重回归);② water-quality 补 GB 3838 阈值表(把 Q047 从必败拉到 1/3 翻盘)。两者均为"软件层"修复,**未消除 9B 的方差与卡死倾向**。
5. **适用建议**:生产环境继续用 27B;9B 适合"简单查询 + 可容忍偶发失败/可重试"的场景;若必须全面上 9B,还需补"机制层硬约束"(收敛 schema 探查工具)+ 重试/投票。

## 1. 背景与模型切换

### 1.1 模型版本

- **27B**:`Qwen3.6-27B-Q5_K_S.gguf`,端点 `http://172.28.101.81:8080/v1`。仓库内 `eval_e2e` 报告头与 `docs/古运河查询性能瓶颈分析.md` **明确标注**,并量化其 ~33 tok/s 为"27B-Q5 单卡硬件地板"。7/28–8/3 的全量基线均为此模型。
- **9B**:用户述为 `qwen3.5-9b`,用于本周(8/4 起)测试。

> ⚠️ **诚实性说明**:仓库内**未找到任何直接写明"9B/换模型"的文字证据**(grep `9B / qwen*9 / 换模型 / 本周` 在所有 md/log/报告头中无匹配;Gateway 报告头一律写"模型: 平台默认",从不点名)。9B 身份来自用户说明,并由 8/4 起的回归数据(乱码输出、轮次=1、sqls=0、同题高方差)间接印证。如需在正式文档中写"换 9B",建议向平台侧核对版本号。

### 1.2 为什么对比这两个模型

评估在"把生产模型从 27B 降到 9B"这一设想下进行,关心三件事:**① 能力掉多少、掉在哪;② 既有的 skill 优化是否能平移;③ 9B 要达到可用还差什么**。本报告即围绕这三点展开。

## 2. 评测方法

| 项目 | 设定 |
|------|------|
| 用例集 | `skills/docs/test-cases-with-sql.md`,98 题(L1=15 / L2=21 / L3=62),覆盖 6 skill |
| 执行 | `scripts/evaluate_deerflow_gateway.py --all-skills`,经 Gateway 真实 agent 全栈 |
| 单题超时 | 900s;轮次0间歇卡死触发 `round0_stall` 自动重试 1 次 |
| 评分维度 | `has_valid_response`(响应有效)+ `sql_generated`(生成SQL)+ `sql_replay_ok`(期望SQL回放)+ `result_quality`(数值/文本重合)+ `trace_sanity`(轨迹合理) |
| 通过线 | 总分 ≥ 0.6 |
| 增量落盘 | 每题一条 jsonl,跑完出 `gateway_eval_all_*.json/.md` |

> **评分基准说明**:expected SQL 是"参考答案"而非"绝对真值",部分题的 golden SQL 口径在 7–8 月做过对齐(见 §6);因此跨期比较以"同口径"跑次为准。

## 4. 9B 评测结果(本周)

### 4.1 全量分数(8/4 20:00 → 8/5 00:35,98 题)

| 指标 | 9B(8/4–8/5) | 27B(8/3) |
|------|--------------|----------|
| 平均分 | **0.749** | 0.864 |
| 中位分 | 0.795 | — |
| 通过率 | **88/98 = 89.8%** | 96.9% |
| 成功生成 SQL | 89/98 | ~98/98 |
| 出错/超时 | 2(`round0_stall`) | — |
| 单题均时 | 151s(max 657s) | ~60–80s/轮 × 多轮 |
| LLM 轮次 | 均 14.8(max 34) | 均 3–7(部分 12–25) |

> **注**:9B 单题"均时 151s"高于 27B 单轮(60–80s),因为 9B 为补足能力**显著增加了探索轮次**(均 14.8 轮),并非模型本身更慢。这也是 9B 卡死/坍缩高发的诱因之一。

### 4.2 按 skill 拆分(9B vs 27B,Δ = 9B − 27B)

| Skill | 9B 均分 | 9B 通过 | 27B 均分 | **Δ** |
|-------|---------|---------|----------|-------|
| water-situation | 0.836 | 25/25 | 0.867 | **−0.031** |
| gate-pump-operation | 0.813 | 15/15 | 0.880 | −0.067 |
| rainfall | 0.767 | 17/18 | 0.890 | −0.123 |
| water-warning | 0.712 | 12/14 | 0.798 | −0.086 |
| water-forecast | 0.695 | 11/13 | 0.795 | −0.100 |
| **water-quality** | **0.575** | **8/13** | 0.812 | **−0.237** |

**关键洞察**:退化与"领域知识/推理负载"强相关。
- **几乎无损**(Δ≈−0.03 ~ −0.07):water-situation、gate-pump —— 单库、查表语义清晰,9B 能稳定复现 27B 行为。
- **中等退化**(Δ≈−0.08 ~ −0.12):rainfall、water-warning —— 时间窗/聚合口径出错增多。
- **退化最重**(Δ≈−0.10 ~ −0.24):water-forecast、water-quality —— 前者多步、后者需国标评价知识。**water-quality 是 9B 的塌方点(−0.237)**。

### 4.3 9B 期严重事件:坏模型吐 8192 个 `?`(已修复)

8/4 14:49 首跑(68 题后中断)出现灾难性回归:**68/68 题 `final_answer` 全是恰好 8192 个 ASCII `?`(0x3F),`sql_generated=0`、通过 0/68、均分 0.223**。

- **定性**:非"9B 能力弱",而是**模型 serving 接入坏**(tokenizer/词表或输出链路字符集问题),模型退化为重复 UNK/无效 token 直到打满 `max_tokens=8192`。
- **判据**:`0x3F` 非 `U+FFFD`(排除 eval 解码 bug);expected SQL 中文完好(排除测试数据损坏);每题输出长度恒为 8192(确定性退化,非能力连续下降)。
- **处置**:平台侧重修(具体由用户完成),8/4 20:00 重跑恢复正常 → 即本报告 9B 数据。**此事件说明 9B 接入对配置敏感,运维需预留校验**。

### 4.4 water-quality 深挖(9B 塌方点根因)

5 道未过题(Q044/Q045/Q047/Q048/Q055)的 tool_trace 显示**两种 9B 特有失败模式**:

1. **schema 探索死循环**:反复调用 `water-db_get_table_schema`(单题 6–8 次)直到耗尽轮次,**从不前进到真正的查询**,产出 SQL=0。SKILL.md 已明确"禁 schema 探查、列名照抄",9B 仍忽略该文字禁令。27B 同题能很快跳出探索转入 query。
2. **多轮后回答坍缩**:如 Q047 一次跑 28 轮、22 条 SQL,最终回答却是 `## SESSION INTENT None …`(未合成结论)。

**方差极大**(同题 Q047 四次重跑:0.25 / 0.30 / 0.44 / 0.65)。6 题重跑(含 1 对照)均分 0.341 → 0.644、通过 1/6 → 4/6,说明**原跑的 0.575 被方差 + stall 压低,真实水平 ~0.65,但仍显著低于 27B 的 ~0.89**。

## 5. 本轮(9B 期)两轮干预

### 5.1 干预一:serving 修复(平台侧)

见 §4.3。把"必败(均分 0.223、通过 0)"拉回正常区间(0.749、89.8%)。属**基础设施修复**,与 skill 内容无关。

### 5.2 干预二:water-quality 补 GB 3838-2002 评价阈值表(软件层)

**问题**:Q047(单因子评级)确定性失败。SKILL.md 原本只在 `references/business_rules.md` 给出国标阈值,而 DeerFlow 首遍只加载 SKILL.md → 模型知道"要写 CASE WHEN 6 档",却拿不到阈值数字 → 写不出。

**改动**(`skills/public/water-quality/SKILL.md`):
- 新增模板 ③「水质评级单轮模板」,内含 CODMn/DO/NH3N/TP 四指标的 6 档 CASE WHEN(国标固定值,与 expected SQL 一致);
- 新增 6 档阈值速查表;Workflow 第 3 步加指向。
- 遵守占位符防泄漏约束:站点字面量硬编码、SQL 代码块内无 `{变量}`。

**效果(Q047 同题)**:
| | 样本 | 均分 | 通过 |
|---|------|------|------|
| 改前 | 0.200 / 0.250 | 0.225 | 0/2 |
| 改后 | 0.437 / 0.300 / 0.650 | **0.462** | **1/3** |

**判断**:净收益明确(**均分翻倍、从必败到有机会过**),且国标阈值本就该在首遍可见层 —— **保留此改动,不回滚**。但它**未确定性修好 Q047**:9B 的 schema 死循环与回答坍缩仍在,属模型 agentic 控制力短板,文字禁令压不住。Q044(模糊问法)未触及,仍确定性失败。

## 6. 既有 skill 优化迭代史(主要在 27B 期完成,对 9B 同样生效)

四条主线(出自 git log + `skills/docs/` 分析文档):

### 6.1 SQL 占位符照抄根治
- 根因:`water-situation/SKILL.md` 内联 SQL 的 ❌ 反例直接写了 `{stcd}`/`{dt}` 占位符,LLM 分不清反例/模板,照抄。
- 修复:剥离 SKILL.md SQL 代码块中的占位符。
- 回归:Q098 0.490→**0.790**、Q014 0.663→**0.700**、Q094 0.695→**0.933**。

### 6.2 golden SQL 对齐 + 评测器重写
- 修正 7 条 golden SQL 聚合口径(Q028/Q030 类);评测器改为从 event-store 评分,修 3 个评分 bug 与 `parse_run_messages` 解析错位(曾把正常轨迹误判为 0)。
- 影响:Q018/Q028 由"假性 0 分"恢复为真实轨迹评分。

### 6.3 单轮模板 + 高频规则前置
- 把"站点列 JOIN / MAX(tm) 锚定 / 派生表替代相关子查询 / 禁反问默认时间窗 / pip 禁令"等高频规则搬进 always-loaded 的 SKILL.md,并配 copy-paste 单轮模板。
- 意图:减少 LLM 往返、在"仅加载 SKILL.md"的约束下保证关键规则可见。**这是 9B 还能守住 89.8% 的重要支撑**(9B 轮次预算更紧,模板直接可抄的优势更大)。

### 6.4 间歇超时兜底 + db.py 超时契约
- 评测脚本加 `round0_stall` 重试(MCP 子进程泄漏 / LLM 500 的兜底);`db.py` 连接级 read_timeout 契约。
- 影响:把"基础设施抖动导致的假性失败"与"真实能力不足"区分开。

### 6.5 全量净效果
- 计划预期:0.847→0.875、94.9%→97.9%。
- 实测(7/31→8/3):**0.847→0.864(+0.017)、94.9%→96.9%(+2.0pp)** —— 基本兑现,略低于计划(Q028/Q030/Q089 仍回退)。

## 7. 适用建议

### 7.1 模型选型

| 场景 | 推荐 | 理由 |
|------|------|------|
| **生产/对外服务**(精度与稳定性优先) | **27B** | 96.9% 通过、同题稳定、water-quality 等领域题靠谱 |
| 内部工具、简单查询、可重试 | **9B 可用** | 简单查表类(water-situation/gate-pump)接近 27B,成本/延迟更低 |
| water-quality 评价、water-forecast、复杂 L3 融合 | **避免 9B** | 9B 退化最重且高方差,易卡死或坍缩 |
| 成本敏感、且可接受 ~90% 通过 + 重试 | 9B + 兜底机制 | 见 7.2 |

### 7.2 若必须全面上 9B,还需补的"机制层硬约束"

> 软件层(阈值表、模板、占位符根治)已尽力;9B 剩余问题需机制层解决。

1. **收敛 `water-db_get_table_schema` 工具**:skill 已给"免探查列",9B 却反复调它陷入死循环。文字禁令它不听,**工具不暴露就没法 loop**。预期同时压住 Q044/Q047 的 schema 死循环模式。(改动涉及 gateway/MCP 工具暴露面,需先定位注册点再动。)
2. **重试 / 多数投票**:9B 同题方差大(Q047 4 次跑有一次过)。对高价值查询跑 2–3 次取最优/多数,可把"有机会过"提到"大概率过",代价是延迟翻倍。
3. **轮次预算 + 强制收束**:对 9B 设更激进的"超过 N 轮仍未执行 query 则强制用模板收束",防止多轮后回答坍缩(§4.4 模式二)。
4. **serving 校验常态化**:8/4 的 8192-`?` 事件表明 9B 接入对配置敏感,上线前应有"吐 `?`/UNK"的自动 smoke 校验。

### 7.3 skill 层下一步(模型无关,做了两个模型都受益)

- 继续把各 skill 的"领域固定知识"(如水质的国标阈值、预报的 type 映射)从 references 上提到 SKILL.md 首遍可见层 —— 本轮 water-quality 阈值表即此思路,可复刻到 water-forecast。
- 维持占位符防泄漏纪律(SQL 代码块禁 `{变量}`,只在禁令文字里出现)。

---

## 8. 结论

- **27B 是当前经过充分优化、可上生产的基线**(0.864 / 96.9%,稳定)。
- **9B 退一档但仍可用**(0.749 / 89.8%),退化集中在领域推理类 skill,且伴随高方差与卡死倾向。
- **既有的 skill 优化(占位符根治 / 单轮模板 / golden 对齐 / 超时兜底)对 9B 同样有效**,是 9B 可用性的主要支撑。
- **本轮两轮干预**:serving 修复(救回灾难性回归)+ water-quality 阈值表(Q047 必败→1/3 翻盘)均有净收益并保留;但**未消除 9B 的方差与卡死**。
- **要 9B 达到接近 27B 的稳定度,缺的是"机制层硬约束"(schema 工具收敛 + 重试 + 轮次收束),而非更多 SKILL.md 文字**。
